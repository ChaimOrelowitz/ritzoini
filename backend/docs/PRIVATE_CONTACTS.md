# Private iPhone Contacts & "Message DSC"

Two private, read-only surfaces that put Ritzoini data on a phone without
giving the phone any way to write back:

| Surface | Endpoint | Consumer |
|---|---|---|
| CardDAV address books | `/carddav/…` | iPhone **Contacts** |
| DSC recipient feed | `/api/dsc/…` | Apple **Shortcuts** |

Neither is reachable without a credential, and nothing here sends a message —
the recipient feed answers *who* to message and the iPhone opens each
conversation itself through Apple Messages. No Twilio, no A2P registration,
no third party ever sees a peer's number.

---

## 1. Who is on the list

### `DSC Peers`

A peer appears when **all** of these hold, evaluated fresh on every request
against Eastern-time "today" (`todayET()`, the same clock the caseload sync
stamps entry and exit dates with):

1. A `ps_caseload_periods` row exists for them with
   `supervisor_airtable_id = AIRTABLE_SUPERVISOR_RECORD_ID`.
2. `entered_on <= today` — a hand-entered future assignment has not started.
3. `left_on IS NULL` **or** `left_on > today` — `syncCaseload` stamps `left_on`
   with today's date the moment a peer drops off Airtable, so a period closed
   today is already over.
4. A matching `ps_peers` row exists (the mirrored name/phone/email/cohort).

Rules 2 and 3 refine what `GET /api/ps/caseload` does (that route selects open
periods alone).

`ps_peers.status` is deliberately **not** part of the rule. 2 of the 27 open
periods belong to peers Airtable marks `Inactive`; they are still on the
caseload, so they still belong in the supervisor's phone and still receive
messages. Caseload membership is the whole rule.

The Caseload and Payroll pages are untouched by any of this.

### `Ritzoini Instructors`

Every row of the `instructors` table. That table defines **no** active/inactive
column and **no** end date, so there is no activity rule to honour — and no
`email` column either, so instructor cards carry name and mobile only.

### Both books

- Records with no usable mobile still appear in **Contacts** (a peer with only
  an email is still a peer) but are excluded from **message recipients**.
- Contacts are ordered by last name, then first name, then id — deterministic,
  which is what keeps collection ETags stable between syncs.

## 2. Configuration

All values are generated by one script:

```bash
cd backend
node scripts/make-contact-credentials.js
```

It prints the four environment variables plus the iPhone password and the
Shortcut bearer token. **The password and token are shown once** — only a
scrypt verifier is stored server-side, so a leaked environment cannot be
replayed as a login. Put them in a password manager.

| Variable | Purpose |
|---|---|
| `CARDDAV_USERNAME` | Basic-auth username the iPhone sends |
| `CARDDAV_PASSWORD_SALT` | 16-byte hex salt |
| `CARDDAV_PASSWORD_HASH` | scrypt verifier of the CardDAV password |
| `DSC_SHORTCUT_TOKEN` | Bearer token for `/api/dsc/*` (min 24 chars) |

**Fail-closed:** if any CardDAV variable is missing or malformed, every
`/carddav` route answers `503` and never queries Supabase. Same for
`/api/dsc/*` if `DSC_SHORTCUT_TOKEN` is missing or shorter than 24 characters.
Both also refuse to run if `SUPABASE_URL` / `SUPABASE_SERVICE_KEY` are absent.

### Deployment

Add the four variables in **Render → the backend service → Environment**, then
redeploy. No database migration is required — this feature reads
`ps_caseload_periods`, `ps_peers` and `instructors` as they already exist and
writes nothing.

No DNS change is required either: `ritzoini.onrender.com` already resolves and
already terminates TLS. If a custom hostname is ever preferred, point a CNAME
at the Render service and use that hostname in the iPhone account instead.

**HTTPS is mandatory in production.** When `NODE_ENV=production`, any request
arriving with `X-Forwarded-Proto` other than `https` is refused with `403` —
Basic-auth credentials must never cross the wire in the clear. `server.js` sets
`trust proxy` so Render's forwarded scheme and client IP are read correctly.

## 3. iPhone CardDAV setup

**Settings → Apps → Contacts → Contacts Accounts → Add Account → Other →
Add CardDAV Account**

| Field | Value |
|---|---|
| **Account type** | CardDAV (under "Other", *not* iCloud/Google/Exchange) |
| **Server** | `ritzoini.onrender.com` |
| **User Name** | the `CARDDAV_USERNAME` value (`ritzoini` by default) |
| **Password** | the password printed by `make-contact-credentials.js` |
| **Description** | `Ritzoini` |
| **Use SSL** | **On** (Advanced Settings — on by default; it must stay on) |
| **Port** | `443` — standard, leave blank |
| **Account URL** | leave blank; discovery handles it |

Enter the hostname alone — no scheme, no path. iOS discovers the rest by
requesting `/.well-known/carddav`, which redirects to `/carddav/`, then walking
`current-user-principal` → `addressbook-home-set` → the two books. If a build
of iOS insists on a full path, set **Advanced Settings → Account URL** to
`https://ritzoini.onrender.com/carddav/principals/dsc/`.

After **Next** verifies the account, make sure **Contacts** is toggled on. Two
new groups appear in Contacts → Groups: **DSC Peers** and
**Ritzoini Instructors**. Each peer card carries their cohort in three places —
`ORG` (shown as Company / Department), `CATEGORIES`, and `X-RITZOINI-COHORT`.

**Edits made on the phone do not stick.** Every write method is refused with
`403`, and the next sync re-serves the server's version. Ritzoini and Airtable
remain the only places anything changes.

## 4. The "Message DSC" Shortcut

Server-side there are two endpoints, both `GET`, both requiring
`Authorization: Bearer <DSC_SHORTCUT_TOKEN>`:

```
GET /api/dsc/audiences
  → { labels: ["All active DSC peers (25)", "Cohort A (14)", …],
      keys_by_label: { "All active DSC peers (25)": "all", "Cohort A (14)": "cohort:A", … },
      audiences: [ { key, label, count, menu_label }, … ] }

GET /api/dsc/recipients?audience=all | cohort:A
  → { audience, audience_label, count,
      recipients: [ { id, name, phone, cohort }, … ] }
```

`phone` is always E.164 (`+15551234567`). Both endpoints are built from the
same de-duplicated list — recipients without a usable mobile removed, two peers
sharing a handset collapsed — so an audience's `count` is exactly the number of
conversations that will open. (The CardDAV book does *not* collapse a shared
handset: two people who share a phone are still two contacts.) An unrecognised audience is
rejected with `400` rather than quietly falling back to everyone.

### Building it

New Shortcut, named **Message DSC**. Add these actions in order. `BASE` is
`https://ritzoini.onrender.com` and `TOKEN` is your `DSC_SHORTCUT_TOKEN`.

**Fetch the audiences**

1. **Get Contents of URL**
   - URL `BASE/api/dsc/audiences`
   - Method **GET**
   - Headers: `Authorization` → `Bearer TOKEN`
2. **If** — `Contents of URL` **has any value**
   - *Otherwise* → **Show Alert** "Couldn't reach Ritzoini. Try again." →
     **Stop This Shortcut**
   - (Also turn **off** "Show When Run" on the Get Contents action so a network
     error surfaces through your alert rather than a system dialog.)

**Choose the audience**

3. **Get Dictionary Value** — Get **Value** for `labels` in `Contents of URL`
4. **Choose from List** — from the previous result, prompt
   *"Who should get this?"*, "Select Multiple" **off**
5. **Get Dictionary Value** — Get **Value** for `keys_by_label` in
   `Contents of URL` → rename this variable **KeyMap**
6. **Get Dictionary Value** — Get **Value** for **Chosen Item** in **KeyMap**
   → rename **AudienceKey**

   *(Step 5–6 is why the API ships `keys_by_label`: Choose from List returns the
   chosen string, not an index, so the map turns it straight into a key.)*

**Fetch the recipients**

7. **Text** — `BASE/api/dsc/recipients?audience=AudienceKey`
8. **Get Contents of URL** — URL = the Text above, **GET**, same
   `Authorization` header
9. **Get Dictionary Value** — `count` → rename **Count**
10. **Get Dictionary Value** — `recipients` in the step-8 result → rename
    **Recipients**
11. **If** — **Count** **is** `0` → **Show Alert** "Nobody on that list right
    now." → **Stop This Shortcut**

**Compose and confirm**

12. **Ask for Input** — Text, prompt *"Message to send"* → rename **Body**
13. **If** — **Body** **has any value**; *Otherwise* → **Stop This Shortcut**
14. **Show Alert** — *"Send this to Count peers, one at a time?"*, message =
    **Body**, **Show Cancel Button ON**. Cancel stops the shortcut, so this is
    the confirmation gate.

**Guard against a duplicate send**

15. **Text** — `AudienceKey|Body` → rename **SendKey**
16. **Get File** — Service **Shortcuts**, path `MessageDSC/last-send.txt`,
    **Error If Not Found OFF**
17. **If** — the file **is** **SendKey** → **Show Alert** *"You already sent
    exactly this. Send again?"* with **Show Cancel Button ON**
18. **Save File** — **SendKey** to Shortcuts / `MessageDSC/last-send.txt`,
    **Overwrite If File Exists ON**

**Send, one conversation each**

19. **Repeat with Each** — item = **Recipients**
    1. **Get Dictionary Value** — `phone` in **Repeat Item**
    2. **If** — that value **has any value**
       - **Send Message** — Recipients = the phone value, Message = **Body**,
         **Show When Run OFF**
       - *Otherwise* → **Text** `Repeat Item.name` → **Add to Variable**
         **Skipped**
20. **Show Result** — *"Sent to Count. Skipped: Skipped"*

### Why this never makes a group chat

Every **Send Message** runs inside **Repeat with Each** with exactly one
recipient in its Recipients field. iOS creates a group conversation only when a
single Send Message action carries two or more recipients — so never pass
**Recipients** (the list) to Send Message, only **Repeat Item**'s `phone`.

### First run

iOS asks once for permission to send messages. Grant it, or every send fails
silently. Test with `cohort:` picked as a small cohort, or temporarily point
step 7 at a cohort you know is small, before running against **All**.

### Failure handling recap

| Situation | What happens |
|---|---|
| Backend down / bad token | Step 2 alert, shortcut stops |
| Audience now empty | Step 11 alert, shortcut stops |
| Empty message | Step 13 stops, nothing sent |
| Peer has no mobile | Excluded server-side; step 19.2 catches any straggler and lists them in **Skipped** |
| Same message re-run | Step 17 warns before anything is sent |
| Wrong audience typed into the URL | Server answers `400`, step 2's pattern catches it |

## 5. Security properties

- **Read-only, structurally.** The CardDAV router has no Supabase write call in
  it. `PUT`, `POST`, `DELETE`, `PATCH`, `PROPPATCH`, `MKCOL`, `MKCALENDAR`,
  `COPY`, `MOVE`, `LOCK`, `UNLOCK`, `ACL`, `BIND`, `REBIND` and `UNBIND` are all
  refused with `403` before reaching a handler.
- **Authenticated everywhere.** Discovery, collections and individual cards all
  require credentials — including `/.well-known/carddav` and `PROPFIND /`.
  There is no unauthenticated path that returns a name, a number or an email.
- **Separate credentials.** CardDAV uses its own Basic pair because iPhone
  Contacts cannot obtain or refresh a Supabase JWT. The Shortcut uses a scoped
  bearer token. Neither grants access to any other Ritzoini route, and neither
  is a Supabase credential.
- **Hashed verifier, constant-time compare.** Only scrypt output is stored.
  Username and token comparisons hash both sides first so `timingSafeEqual`
  always sees equal lengths and no comparison leaks length or content.
- **No secrets in URLs.** Both surfaces read `Authorization` headers only; a
  token in the query string does not authenticate.
- **Rate limited.** 600 requests / 5 min for CardDAV sync bursts, 120 for
  discovery, 60 for `/api/dsc/*`.
- **No-store.** Every response carries
  `Cache-Control: no-store, no-cache, must-revalidate, private`, plus
  `nosniff` and `no-referrer`.
- **Privacy-safe logs.** Log lines carry method, book slug, member counts and
  status — never a credential, an `Authorization` header, a phone number, an
  email address, a vCard body or a card URL (card URLs embed a peer's record
  id, so a route label is logged instead).

## 6. Tests

```bash
cd backend
npm test        # existing parser suite + this feature's suite
```

`test/dscContacts.test.js` stubs Supabase through `require.cache` and exercises
the real routers over a real HTTP listener: missing/invalid auth, missing
configuration, active vs expired vs future vs closed-today periods, `Inactive`
status, cohort filtering, unknown-cohort rejection, phoneless exclusion,
duplicate-number collapsing, menu counts matching the send list, deterministic
ordering, CardDAV discovery and
listing, stable UIDs/ETags/bodies, sync-token behaviour, rejection of every
write method, and the absence of contact data in every unauthenticated
response.
